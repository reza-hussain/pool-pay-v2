# Organizer payment gates inviting (not Pool creation), for every Pool type

Supersedes part of ADR-0016 (see that file's note and the "Consequences" bullet this replaces).

ADR-0016 established the right invariant — the Organizer pays their own share before inviting anyone else — but described the mechanics in a way that reads as blocking the Pool's *existence* on payment ("a Member does not exist until they pay... the Organizer... pay[s] as part of *creating* the Pool"). That's not what shipped (#58/PR #65): `PoolService.createPool` creates the `Pool` row immediately for every type; for `CUSTOM_SPLIT` it defers only the Organizer's *Membership*, via a self-addressed pending `Invitation`. The Pool exists and is visible to its Organizer right away — they just can't invite anyone until that Invitation is paid.

This ADR restates that mechanic accurately, and extends it to Equal Split Pools, which ADR-0016 explicitly exempted ("Equal Split Pools are unaffected... Invite Link/Pool Code joining stays immediate"). Today `createPool` gives an Equal Split Organizer an unconditional `Membership` the instant the Pool is created — no payment gate at all. That inconsistency (Custom Split gated, Equal Split not) is what this ADR closes.

## Decision

1. **Pool creation always succeeds immediately and unconditionally**, for both Equal Split and Custom Split. The Organizer lands on that Pool's Dashboard right away — creation is never blocked on payment.
2. **Until the Organizer's own share is paid, the Dashboard is locked**: "Add Members" (and any other invite action — Invite Link, Pool Code, sending a Custom Split Invitation) is disabled. This is the existing "Awaiting Payment" → "Add Members Unlocked" Dashboard pattern already mocked in Stitch, now applied to both Pool types.
3. **Mechanism: reuse Custom Split's Invitation-based deferral for Equal Split too.** At creation, instead of an immediate `Membership`, the Organizer gets a self-addressed pending `Invitation` for their own share (`perPersonAmountPaise` for Equal Split, same as the existing `organizerShareAmountPaise` path for Custom Split). Paying it — via the existing Deposit/QR flow — atomically creates the `Membership` and marks the `Invitation` paid, exactly as ADR-0016 already specified for Custom Split. "Does the Organizer have a Membership yet" remains the single source of truth for whether the Dashboard is unlocked — no new gate flag needed on `Pool` itself.
4. **On the "set amount" step, Pay Now stays primary (pumpkin), Pay Later stays secondary (outline) — no change in visual hierarchy.** Choosing Pay Later doesn't fail Pool creation; it lands the Organizer on the locked Dashboard instead of on the unlocked one.
5. **An unpaid Pool auto-expires 24 hours after creation — lazily, no cron job.** This codebase already has a no-sweep expiry convention: `OtpRequest.expiresAt` (`auth-service.ts`) is checked at the point of use and never proactively swept. The Organizer's self-Invitation lapsing (still `PENDING` at `expiresAt`) follows the same shape — discovered, and persisted as `EXPIRED` (row kept, soft-cancel, not deleted, matching how a removed `Membership` or an expired `Invitation` are already kept elsewhere in this codebase), the next time something actually touches the Pool (a Deposit attempt, a join/invite attempt) — not by a background job. An `EXPIRED` Pool accepts no further Deposits and cannot be paid into — same terminal treatment as an expired/cancelled Invitation. Unlike `CLOSED`, no refund logic runs: nothing was ever collected, since the Organizer's own share — the only money an unpaid Pool could have received — was never paid.
6. **This changes an already-shipped constant.** `ORGANIZER_INVITATION_EXPIRY_MS` in `pool-service.ts` is currently `7 * 24 * 60 * 60 * 1000` (7 days) for Custom Split's self-Invitation. This ADR's 24-hour window applies uniformly to both types, so that constant drops to `24 * 60 * 60 * 1000` as part of implementing this — existing unpaid Custom Split Pools are affected, not just new Equal Split ones.

## Considered Options

- **Gate Equal Split with a different mechanism than Invitation** (e.g. a boolean flag on `Pool`, or a bare "unpaid" `Membership` row). Rejected — Invitation already models exactly the state machine needed (`PENDING` → `PAID`/`EXPIRED`/`CANCELLED`, with `expiresAt`), and reusing it keeps one mechanism for "Organizer hasn't paid their own share yet" across both Pool types instead of two parallel ones.
- **No expiry — stay locked indefinitely until paid.** Considered, but an abandoned unpaid Pool with no expiry has no cleanup path and no precedent elsewhere in the schema (Invitations to other Members already expire). Rejected in favor of the 24-hour auto-expiry in point 5.
- **Amend ADR-0016 directly instead of writing a new ADR.** Rejected — 0016 explicitly scoped itself to Custom Split and named Equal Split as an explicit non-goal in its own Consequences; overwriting that text would erase the record that the exemption was a deliberate, later-reversed decision rather than an oversight.

## Consequences

- ADR-0016's Consequences bullet "Equal Split Pools are unaffected: Invite Link/Pool Code joining stays immediate" is superseded by this ADR. Equal Split Pool creation still uses Invite Link/Pool Code for *other* Members joining (unchanged) — only the Organizer's own first share is now gated the same way Custom Split's already is.
- `Pool.state` gains a fourth value, `EXPIRED`, alongside `ACTIVE` | `LOCKED` | `CLOSED`.
- Equal Split's `createPool` path changes from "create `Membership` immediately" to "create self-addressed `Invitation`, create `Membership` on payment" — mirroring the Custom Split branch in `PoolService.createPool` rather than being a parallel special case.
- `PENDING` self-Invitations past their `expiresAt` transition to `EXPIRED` (Pool + Invitation) lazily, at the next Deposit/join/invite touch — no background sweep, matching `OtpRequest.expiresAt`'s existing no-cron pattern. Custom Split's 7-day (now 24-hour) self-Invitations had, until this ADR's implementation, nothing enforcing their own expiry at all.
- Mobile needs new screens: this repo currently has *no* Custom Split creation UI (`CreatePoolScreen.tsx` only creates `EQUAL_SPLIT`, and `App.tsx` routes pool creation straight to Invite unconditionally) and no locked-Dashboard state UI at all. Both are new build, using the Stitch mockups (project `3891501608534528478`) as the visual reference: "Create Pool - Set Amount" (unified step-2, both types), "Pool Dashboard - Awaiting Payment" (locked), "Pool Dashboard - Add Members Unlocked" (post-payment).
- `CONTEXT.md`'s **Organizer** and **Invitation** glossary entries need updating to reflect that the self-Invitation/deferred-Membership mechanism now applies to both Pool types, not just Custom Split.
